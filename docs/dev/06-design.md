# FlowSage 设计说明

> 状态：**草案**（2026-09-18 定方向，细节边做边完善）
> 本文是需求与架构的单一来源；实现细节变更时同步更新本文与 `04-progress.md`。

## 1. 一句话定位

**FlowSage 是一个由浏览器驱动的安全运营 Agent**：它托管一个独立浏览器，接管会话、
观测流量、像 Selenium 一样操作页面，并把学到的接口用于实际作业
（当前场景：态势感知告警的批量处置）。

## 2. 与另外两个项目的关系

| 项目 | 角色 | 关系 |
|---|---|---|
| **FlowSage**（本项目，Go） | 浏览器托管、流量观测、页面操控、接口理解、任务编排 | 主体 |
| **alertctl**（`D:\project\python\态势感知告警处理`，Python） | 已验证的处置规则引擎 + 站点接口契约 | **被复用**，不重写 |
| **CyberStrikeAI**（上游，Go） | Agent/Eino/MCP/RBAC/持久化基础设施 | 基线，逐步裁剪渗透相关能力 |

关键约束：`alertctl/smart.py` 的规则话术经 **5832 条历史台账回放验证**（可提交 4259 / 框架类 1541 / 不处置 17 / 需人工 15，无遗漏），
且口径由用户逐类确认。**该逻辑不重写、不交由 LLM 自由生成。**

## 3. 解决的真实痛点

| 现状痛点 | FlowSage 的做法 |
|---|---|
| 登录必须过图形验证码，Cookie 有效期约 3 小时，交班后要人工复制粘贴 | Agent 托管浏览器，人工只在验证码处点一次；会话自动提取、失效自动告警 |
| 换站点 / 换厂商版本要人工抓 HAR、手工推断字段、手写接口层 | Agent 直接读实时流量，产出接口清单与客户端骨架，人工复核后落地 |
| 批量处置要在 Web 界面逐条点弹窗、填话术、传附件 | Agent 用学到的接口逐条提交，话术由已验证的规则引擎生成 |
| 部分操作只能在页面上完成（无对应接口） | Selenium 级页面操控作为兜底通道 |

## 4. 能力清单

| 能力 | 说明 | 阶段 |
|---|---|---|
| **浏览器托管** | 启动独立 Chromium 实例（独立 user-data-dir，不影响日常浏览器），登录态持久化 | MVP-1 |
| **会话接管** | 经 CDP 提取 Cookie/Token；检测失效；可导出为 alertctl 的 `config.toml` / `ALERTCTL_COOKIE` | MVP-1 |
| **流量观测** | CDP Network 域全量捕获请求/响应（含载荷），结构化落库；可导出标准 HAR 1.2 | MVP-2 |
| **页面操控** | Selenium 等价能力：元素定位、点击、输入、等待、截图、执行 JS、多标签页 | MVP-3 |
| **接口理解** | LLM 分析流量 → 产出接口清单（路径/载荷/分页/统一外壳/鉴权），与 alertctl 的 `interfaces.md` 对齐并标出差异 | MVP-4 |
| **任务执行** | 列告警 → 匹配规则生成话术 → 传附件 → 提交处置；复用 Python 规则引擎 | MVP-4 |
| **Agent 化** | 上述能力注册为 MCP 工具，由 FlowSage 的 Eino Agent 编排调用 | MVP-3 起 |

## 5. 架构

```
┌──────────────────────────────────────────────────────────────┐
│  交互层：CLI 子命令 + Agent 对话（复用上游 Web 控制台/机器人）  │
└───────────────────────────┬──────────────────────────────────┘
                            │  MCP 工具调用
┌───────────────────────────▼──────────────────────────────────┐
│  FlowSage 核心（Go）                                          │
│  ├ internal/browser    浏览器生命周期、CDP 会话、profile 管理  │
│  ├ internal/traffic    抓包、落库、HAR 导出                    │
│  ├ internal/automation 元素定位/点击/等待/截图/JS（Selenium 级）│
│  ├ internal/apimodel   流量→接口清单（LLM + 结构化规则）        │
│  ├ internal/dispatch   告警作业编排（列告警/话术/附件/提交）    │
│  └ internal/bridge     规则引擎桥接（稳定 JSON 契约）           │
└───────┬────────────────────────────┬─────────────────────────┘
        │ CDP over WebSocket         │ 子进程 / stdio
┌───────▼──────────────┐   ┌─────────▼─────────────────────────┐
│ 独立 Chromium 实例    │   │ alertctl 规则引擎（Python）        │
│ Chrome→Edge→便携版   │   │ smart.analyze() → HandlePlan JSON │
└──────────────────────┘   └───────────────────────────────────┘
```

### 5.1 浏览器来源优先级

| 顺序 | 来源 | 场景 |
|---|---|---|
| 1 | 系统 Chrome | 有则优先 |
| 2 | 系统 Edge | **Windows 10+ 默认存在**（本机实测 Edge 153 可用） |
| 3 | 随包便携 Chromium | 离线老机器 / 无浏览器兜底 |

独立实例通过 `--user-data-dir=<工作区>/browser-profile` 实现：
不干扰日常浏览器，且登录态可跨重启保留。

### 5.2 规则引擎的集成边界（重要）

**不改 `smart.py` 的逻辑**，只在 Python 侧加一层薄壳，用稳定的 JSON 契约通信：

```
输入：归一化告警 JSON（等价 alertctl 的 Alert 模型 + reasons 字典）
输出：HandlePlan JSON —— {status, reason_name, message, note, submittable}
```

契约与现有 `alertctl/models.py::HandlePlan` 完全一致，因此：
- Python 侧改动量≈0，已验证的 66 项断言继续有效
- Go 侧可用子进程或 MCP 两种方式接入（优先子进程，实现简单、无网络依赖）
- 未来若需 Go 原生实现，可拿现有 66 项断言作为验收门槛

### 5.3 流量与数据落库

| 数据 | 位置 | 说明 |
|---|---|---|
| 浏览器 profile | `<工作区>/browser-profile/` | 登录态，含 Cookie，**不进版本库** |
| 流量记录 | SQLite（新增表，或独立 `traffic.db`） | 请求/响应结构化记录 |
| HAR 导出 | 用户指定路径 | 标准 HAR 1.2，可直接喂给现有分析流程 |
| 接口清单 | Markdown/JSON | 与 alertctl 的 `references/interfaces.md` 对齐 |

## 6. 分阶段实施

| 阶段 | 交付 | 验收标准 |
|---|---|---|
| **MVP-1** 浏览器托管 + 会话接管 | `flowsage browser open <url>`：独立 profile 启动、人工登录、自动提取 Cookie、失效检测 | 能完全替代"手工从浏览器复制 Cookie 粘进 config.toml"，并把 Cookie 直接喂给现有 alertctl |
| **MVP-2** 流量观测 | 全量捕获 + 落库 + `flowsage traffic export --har out.har` | 走一遍登录+处置流程，导出的 HAR 与人工从 DevTools 导出的等价 |
| **MVP-3** 页面操控 + Agent 化 | 定位/点击/输入/等待/截图/JS，并注册为 MCP 工具 | Agent 能自主完成"打开告警列表 → 翻页 → 截图 → 返回结构化结果" |
| **MVP-4** 接口理解 + 端到端处置 | LLM 接口清单生成；桥接规则引擎；列告警→话术→附件→提交 | 跑通今日未处置告警的完整处置链路，且话术与 alertctl 现有口径逐字一致 |

每个阶段独立可交付，前一个阶段的产物不阻塞后续。

## 7. 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 浏览器驱动 | **chromedp**（CDP 原生） | 需要直接订阅 Network 域事件做全量抓包，chromedp 对原始 CDP 最直接 |
| 备选 | rod | 元素等待等 API 更 Selenium 化；若 chromedp 写页面操控太啰嗦可局部换用 |
| 抓包方式 | CDP Network 域 | 不依赖中间人证书，不需要改系统代理 |
| 规则引擎 | Python 子进程 + JSON 契约 | 保留已验证逻辑，隔离运行时不引入编译期耦合 |
| Agent 编排 | 复用上游 Eino + MCP | 不重复造轮子 |
| 持久化 | SQLite（复用上游） | 上游已具备，无需引入新依赖 |

## 8. 已知风险与待验证

| 风险 | 影响 | 应对 |
|---|---|---|
| 企业策略可能禁用 Edge 的 CDP | 浏览器方案失效 | 实测；不行则降级到便携 Chromium |
| 站点若走 WebSocket / 加密载荷 | CDP 抓不到明文 | 评估后再定是否需页面层解析兜底 |
| 现场老机器（LTSC 2018 / Win10 1809）兼容性 | 便携 Chromium 可能起不来 | 参考 alertctl 的 Alacritty 兼容经验，保留纯文本/无浏览器降级路径 |
| 抓包含敏感数据（账号、内网拓扑） | 合规风险 | 流量库与 profile 一律 gitignore；提供清理命令 |
| 批量处置接口未证实 | 处置效率 | 沿用 alertctl 现状（逐条），确认后再优化 |

## 10. 不做什么

- **不做自动登录**：登录必须过图形验证码，无法脚本化，且绕过验证码不合规
- **不做告警的自动值守/无人处置**：话术口径需人工确认的场景（框架类、需人工类）一律拦截
- **不重写已验证的处置规则**：`smart.py` 是资产，不是技术债
- **不保留上游的渗透攻击能力**：C2、WebShell、后渗透相关模块在后续阶段评估裁剪
