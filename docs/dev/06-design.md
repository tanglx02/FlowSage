# FlowSage 设计说明

> 状态：**已定稿方向，细节边做边完善**（2026-09-18 二次校准定位）
> 本文是需求与架构的单一来源；实现变更时同步更新本文与 `04-progress.md`。

## 1. 一句话定位

**FlowSage 是一个 Web 端的 AI Agent，把目标 Web 应用自动转换成可维护的 Python 程序。**

给它的输入是**流量**（抓包），产出是**代码**：
读不懂的 Web 系统 → 看得懂的接口清单 → 拿起来就能用的 Python 客户端 / 自动化脚本。

**操作全部在 Web 控制台完成**，不要求用户敲命令行。

## 2. 与相关项目的关系

| 项目 | 角色 | 关系 |
|---|---|---|
| **FlowSage**（本项目，Go） | Web 控制台、流量接入、接口分析、代码生成 | 主体 |
| **alertctl**（`D:\project\python\态势感知告警处理`，Python） | **产出物的手工样板** | 参考其分层与工程规范，不直接复用代码 |
| **CyberStrikeAI**（上游，Go） | Agent/Eino/MCP/RBAC/Web 控制台基础设施 | 基线；渗透能力整体剥离 |

> **alertctl 的定位变了**：它从"要复用的规则引擎"变成"**目标产出物的样板**"。
> 它是一个人手工做出来的"Web 应用 → Python 程序"成果，FlowSage 要做的是把这条路径自动化。
> 它的 `技术功能实现文档.md` 是产出物工程规范的参考（分层、便携打包、验证脚本）。

## 3. 三个功能

| # | 功能 | 输入 | 产出 | 一句话 |
|---|---|---|---|---|
| **F1** | 流量 → CLI/TUI 程序 | 抓包流量 | Python CLI/TUI 客户端 | 把 Web 应用做成**命令行可交互**的程序 |
| **F2** | 浏览器 → 自动化程序 | 页面操作过程 | Python Selenium 式脚本 | 把 Web 应用做成**自动化可回放**的程序 |
| **F3** | API 分析 | 抓包流量 | 接口清单 | 找出目标 Web 应用的**所有** API 接口 |

依赖关系：**F3 是地基**，F1 与 F2 都建立在接口清单之上。

### 3.1 F1 流量 → CLI/TUI 程序

从流量归纳出接口，生成一个 Python 程序，让原本只能在网页上点的操作变成命令行操作。

产出物形态参考 alertctl：

```
生成的客户端/
├── <app>ctl/
│   ├── cli.py        入口与参数
│   ├── config.py     配置加载（base_url / cookie / 超时）
│   ├── models.py     归一化模型
│   ├── session.py    HTTP 会话与统一拆包
│   ├── sources/      数据源（真实站点 / mock）
│   └── tui.py        全屏界面（Textual），另带纯文本保底模式
├── config.example.toml
└── requirements.txt
```

### 3.2 F2 浏览器 → 自动化程序

观察人在页面上的操作（点击、输入、翻页）与页面结构，生成可回放的自动化脚本。

产出物形态：Python + Selenium/Playwright 脚本，含显式等待、选择器常量表、断言与截图留证。

### 3.3 F3 API 分析

从流量里把接口全部挖出来，并理解每个接口：

| 分析维度 | 说明 |
|---|---|
| 端点清单 | 方法 + 路径 + 出现次数 + 状态码 |
| 静态资源过滤 | JS / CSS / 图片自动剔除（实测某站点 286 条流量里只有 49 条是接口） |
| 路径参数识别 | 形如 `/alarms/{id}` 的 ID 段自动泛化 |
| 请求结构 | Query / Body 字段、类型、必填推断 |
| 响应结构 | 字段树、数组元素结构 |
| 统一外壳 | 识别 `{code, data, msg}` 这类包装层 |
| 分页模式 | `pageNo/pageSize`、`list/total` 等模式识别 |
| 鉴权方式 | Cookie / Bearer / OAuth2 token 端点 |
| 接口分组 | 按路径前缀归纳为功能模块（如 `alarms`、`sysUser`、`attchment`） |

## 4. 流量从哪来（四种通道）

用户已确认四种全做，按实现优先级排列：

| 优先级 | 通道 | 原理 | 优点 | 代价 |
|---|---|---|---|---|
| 1 | **HAR 文件导入** | 上传 DevTools 导出的 `.har` | 最简单可靠、可离线、可复现；已有真实样本可验证 | 需人工导出一次 |
| 2 | **浏览器扩展** | 上游已有 DevTools 扩展（v0.3.10）抓 Network 回传 | **用你自己的浏览器**，登录态与验证码天然解决 | 需装扩展 |
| 3 | **托管浏览器** | 服务器拉起独立 Chromium，CDP 抓包（MVP-1 已实现） | 全自动、不依赖用户浏览器 | 需在托管窗口里登录；受企业策略影响 |
| 4 | **CDP 连现有浏览器** | 连用户手动开的 `--remote-debugging-port` 实例 | 复用现有登录态与扩展 | 需用户多一步启动操作 |

统一抽象：四种通道最终都产出**同一份归一化流量记录**，分析引擎只认这一种格式。

## 6. Web 控制台（精简后）

从上游控制台摘掉渗透相关页面，导航只保留：

| 菜单 | 内容 |
|---|---|
| **项目** | 一个目标 Web 应用 = 一个项目（base_url、站点名、备注） |
| **流量** | 导入 HAR / 连接扩展 / 托管浏览器 / CDP 连接；流量列表与详情 |
| **接口** | 分析结果：接口清单、字段结构、分组；可人工编辑与确认 |
| **生成** | 选择接口 → 生成 Python CLI / Selenium 脚本；预览、下载、历史版本 |
| **对话** | 与 Agent 对话（复用上游 Eino + 多智能体能力） |
| **设置** | 模型通道、会话与凭据 |

实现方式：**路由与菜单层面解除挂载，代码保留在仓库**（便于后续需要时恢复）。

## 7. Agent Skills（整体替换）

运行时由 Agent 加载的 `skills/` 目录，从 22 个渗透 skill 整体替换为对应新功能的 skill。

| Skill | 用途 | 对应功能 |
|---|---|---|
| `traffic-to-api-inventory` | 从流量归纳接口清单：过滤、去重、参数与结构推断、外壳/分页/鉴权识别 | F3 |
| `web-api-recon` | 主动补全流量里没出现的接口（菜单、前端路由、命名规律） | F3 |
| `web-app-domain-modeling` | 把接口清单抽象成实体/视图/操作，为生成 CLI 做准备 | F1 |
| `python-cli-codegen` | 生成 Python CLI/TUI 客户端（分层与规范对齐 alertctl） | F1 |
| `page-structure-extraction` | 从 DOM/HTML 提取表单、表格、选择器常量 | F1 / F2 |
| `python-selenium-codegen` | 生成 Selenium 自动化脚本（显式等待、选择器表、断言） | F2 |
| `session-auth-handling` | Cookie / Bearer / OAuth2 会话处理与失效检测、验证码人工介入点 | 三者的公共基础 |
| `codegen-verification` | 生成物的自检：mock 回放、断言、冒烟脚本 | 三者的公共收尾 |

> 旧 skill 按用户决定**直接删除**，不在工作区保留存档（需要时从 git 历史取回）。

## 9. 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 后端 | 复用上游 Go + gin + SQLite | 不重复造轮子 |
| 前端 | 复用上游静态前端（原生 JS，无构建步骤） | 加页面成本低 |
| 流量解析 | 自研（HAR 1.2 是公开格式） | 无需引入依赖 |
| 浏览器自动化 | chromedp（已引入） | 需要 CDP 原始能力 |
| 生成物技术栈 | Python 3.10+ / httpx / Textual / Typer | 对齐 alertctl 已验证的选型 |
| LLM 接入 | 复用上游 Eino 多通道 | 已有配置与推理字段支持 |

## 10. 风险与待明确

| 项 | 说明 |
|---|---|
| 生成代码的可用性 | 自动生成的客户端必须能真跑通，因此 P2 的验收必须连真实站点验证，不能只看代码长得对 |
| 站点差异大 | 不同厂商的响应外壳、分页、鉴权差异大，分析引擎要"能识别多种模式"而非硬编码一种 |
| 加密/签名接口 | 若站点对请求做前端签名（如 `sign` 头），生成物需要复现签名算法，属高难点，需评估 |
| WebSocket/SSE | 实时通道不是 HTTP 请求-响应模型，需要单独建模 |
| 生成的代码谁来维护 | 产出物应可直接进版本库维护；生成器需支持"重新生成并保留人工改动"的策略 |
| 待明确 | 生成物的存放位置（服务器侧还是下载到本地）；是否需要"生成物差异对比"功能 |

## 11. 不做什么

- **不做渗透测试能力**：攻击、后渗透、C2、WebShell、漏洞利用等整体剥离
- **不做自动登录绕过**：图形验证码必须人工介入
- **不追求 100% 自动化生成**：生成物需人工复核后再投入使用，工具的价值是"从 0 到 80%"
- **不绑定单一目标系统**：能力是通用的，不针对某个厂商硬编码
