# 生成物验证

**生成的代码"看起来对"不等于"能跑"**。交付前必须过以下关卡。

## 四道关卡

| 关卡 | 前提 | 验什么 | 不过怎么办 |
|---|---|---|---|
| 1. 离线自检 | 无需网络与凭据 | 程序能启动、模型能构造、格式化输出正确 | 改代码 |
| 2. 会话探活 | 需要有效会话 | 鉴权接口返回成功、业务必带头被正确注入 | 检查会话与固定头 |
| 3. 接口冒烟 | 需要有效会话 | 每个接口真实调一次，断言响应结构符合预期 | 对照清单修正 |
| 4. 一致性比对 | 有原始流量 | 生成物的字段名/类型与流量实际响应一致 | 修正模型 |

**关卡 1 与 2 必须做成命令**，让使用者随时能跑：

```bash
python -m <app>ctl --mock      # 关卡 1：离线演示，零真实请求
python -m <app>ctl --check     # 关卡 2：连通性 + 会话 + 关键接口
```

## 关卡 1：离线自检要验什么

- 配置加载：缺失/错误配置给出人话提示，而不是裸异常
- **BOM 兼容**：带 BOM 的 TOML 能被正确读取
- 模型归一化：站点原始字段 → 可读字段的映射正确
- mock 数据源：能列出、能翻页、能进入详情
- 输出格式：无终端特性依赖（纯文本模式在最小终端下也能显示）

## 关卡 2：会话探活

```
1. 读配置或环境变量里的凭据
2. 调一个轻量鉴权接口（如 sysUser/me）
3. 成功 → 打印当前用户/站点信息，退出码 0
4. 失败 → 明确区分三种原因并给出对应指引：
   - 网络不可达
   - 证书问题（自签名场景是否关了校验）
   - 会话失效 → 指引重新获取会话
```

**区分失败原因是关键**：一句"请求失败"会让使用者排查半天。

## 关卡 3：接口冒烟

对清单里每个"只读"接口真实调用一次，断言：

- 统一外壳能被正确拆开（成功码判定是否符合实际）
- 响应结构与清单描述一致（字段存在性、类型）
- 分页参数生效（总数与页大小符合预期）

**写类接口不冒烟**——不要为了验证而对目标产生副作用。写接口的验证放在人工确认后。

## 关卡 4：一致性比对

把生成物声明的字段与**源流量里实际出现过的字段**做差集：

- 声明了但流量里没出现过 → 可疑（可能是猜的），标出来
- 流量里出现过但没声明 → 遗漏，需要补

这项能抓住两类典型错误：**编造字段**与**漏字段**。

## 报告格式

验证结果用表格输出，每条给出结论与证据：

| 检查项 | 结果 | 证据 |
|---|---|---|
| 配置加载 | 通过 | 缺 base_url 时提示"请在 config.toml 填写 base_url" |
| 会话探活 | 通过 | sysUser/me 返回 nickname=xxx |
| 列表接口 | 通过 | 返回 20 条，total=137，与清单一致 |
| 字段一致性 | 1 处遗漏 | 响应含 `riskAggr` 字段，模型未声明 |

**不要用"可能""应该没问题"这类表述**——每条结论都要有可复现的证据。

## 交接

验证不通过时，回到对应环节修正：

- 接口理解错 → `traffic-to-api-inventory`
- 分层/结构问题 → `python-cli-codegen` 或 `python-selenium-codegen`
- 会话问题 → `session-auth-handling`
