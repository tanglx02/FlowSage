# 接口补全（流量之外）

抓包只能覆盖"人点过的路径"。要拿到**全部**接口，需要从前端产物里补。

> 边界：这是**读取公开的前端资源**做静态分析，不涉及漏洞探测、不做未授权访问。

## 三个来源

### 1. 菜单与路由接口

系统通常有"取当前用户可见菜单"的接口（名字多为 `sysMenu/routes`、`getMenus`、`router`）。
它的响应里含**全部功能入口**，据此可以推断出还没访问到的功能页面 → 对应接口。

做法：把菜单树里的每个节点与已有接口清单比对，找出"有页面但没有对应接口"的功能点。

### 2. JS 包里的接口字符串

前端产物里通常硬编码了接口路径。提取思路：

- 从流量里收集所有 `.js` 响应体（Hash 命名的 chunk 文件信息密度最高）
- 搜索形如 `/` 开头且含 `api`/`v1` 的字符串字面量
- 搜索模板拼接：`` `${prefix}/alarms/${id}` `` 这类反引号模板，还原为带参数的路径
- 搜索 axios/fetch 调用点：`url:` / `.get(` / `.post(` 后跟的字符串

**关键**：把提取到的路径与已有清单比对，只输出**新增**的。新增项标注来源（来自哪个 chunk）。

### 3. 命名规律外推

同一模块内接口命名往往有规律。观察到：

```
/alarms/queryAdvPage
/alarms/alarmTypeStats
/alarms/subtypes
```

可以推断同一前缀下可能还存在其他查询/统计接口。**外推结果一律标为"低置信度候选"**，
不得直接进正式清单。

## 输出与使用

| 置信度 | 来源 | 处理 |
|---|---|---|
| 高 | 菜单接口里出现、且与已有清单同前缀 | 可直接进入待确认清单 |
| 中 | 从 JS 里提取到的完整路径字面量 | 进待确认清单，需人工验证 |
| 低 | 从命名规律外推 | 单独列出，仅作提示 |

**所有补全项都要经人工确认后才能进入代码生成**——猜错的接口会污染生成物。

## 验证方式

补全项要尽量验证可用性，验证手段限于：

- 该接口是否出现在前端代码的调用点（有调用点 = 大概率存在）
- 是否与已有接口共享同样的统一外壳与鉴权要求

不要在未授权的情况下对目标发起探测性请求。

## 交接

产出的候选清单交给 `traffic-to-api-inventory` 的输出合并，标注 `source: recon` 与置信度，
由人工在 Web 界面上勾选确认。
