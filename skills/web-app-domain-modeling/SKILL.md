# Web 应用 → 领域模型

接口清单回答"有哪些接口"，领域模型回答"**这个应用能做什么**"。
生成物面向用户的部分（菜单、命令、操作流程）全部由领域模型驱动。

## 三个概念

| 概念 | 含义 | 来源 |
|---|---|---|
| **实体** | 被操作的对象，如"告警""用户""设备" | 响应结构里反复出现的对象类型 |
| **视图** | 实体的列表/详情视角，如"实时告警""历史告警" | 分页接口 + 同样的实体结构 |
| **操作** | 对实体做的事，如"处置""导出""上传附件" | 写类接口（POST/PUT/DELETE） |

## 识别方法

### 实体

看响应里 JSON 对象的结构：**同一组字段在多个接口里重复出现**，就是一个实体。
字段名（`alarmId`、`alarmTitle`、`deviceName`）直接给出实体归属。

一个实体一份模型，字段取并集，标注每个字段出现在哪些接口里。

### 视图

同一实体的分页接口往往有多个，区别在筛选条件：

| 视图 | 特征 |
|---|---|
| 实时/原始 | 条件里带"是否实时"之类的标记 |
| 历史/检索 | 带时间范围条件 |
| 统计 | 返回聚合数值而非列表 |

视图必须记下**固定筛选条件**——这正是用户要点的那些页面。

### 操作

从写类接口反推业务动作，并记录：

- 需要的参数（哪些必填）
- **前置动作**（例如"提交处置前必须先上传附件"这类顺序约束）
- 是否可批量（流量里只见单条提交时，按不可批量处理）
- 是否需要人工确认（如会不可逆改变目标状态的）

## 输出形态

```yaml
实体:
  Alert:
    字段: [id, title, severity, device, src_ip, dst_ip, occurred_at, handled]
    来源接口: [queryAdvPage, alarmsSearch, alarms/{id}]
视图:
  实时告警: {接口: queryAdvPage, 固定条件: {h_is_real_time: "1"}, 分页: 页码式}
  智能告警: {接口: queryAdvPage, 固定条件: {h_is_real_time: "3"}, 默认时间: 当天}
操作:
  处置告警:
    接口: [attchment/batch-upload, alarms/response]
    前置: 每条先上传附件
    批量: 逐条提交
    人工确认: 是
```

这份模型直接决定生成物的菜单结构与命令行接口设计。

## 与生成器的分工

| 层 | 负责 |
|---|---|
| 本 skill | 决定"有哪几个实体/视图/操作、叫什么名字、有什么约束" |
| `python-cli-codegen` | 决定"这些怎么落到 Python 分层结构里" |

**命名要面向使用者**，不要照搬接口名：`处置告警` 而不是 `alarms/response`。
界面里出现的技术术语越少越好。

## 不要做的事

- 不要为了"完整"给每个接口都造一个命令——用户不需要点不到的接口
- 不要把统计接口包装成"操作"，它是视图的一部分
- 约束不明的操作（不知是否需要前置、不知能否批量）标为"待确认"，不要猜
